1. THE TASK IN ONE SENTENCE
---------------------------
Build semantic search over a payment-fraud knowledge base. A user types a question in plain
English and the system returns the most relevant passages by MEANING, not keyword match.
This is the retrieval half of RAG (Retrieval-Augmented Generation).

The five assignment steps:
  1. Create a Qdrant Cloud cluster and run a health check.
  2. Prepare 200+ documents: clean and chunk them.
  3. Embed every chunk with Gemini Embedding 2 (3072 dimensions).
  4. Store the vectors in Qdrant with a payload.
  5. Run 10 natural-language searches plus 1 filtered search.


2. KEY CONCEPTS TO EXPLAIN FIRST (about 1.5 minutes)
----------------------------------------------------
- Embedding: a model turns text into a list of 3072 numbers. Texts with similar meaning get
  vectors that point in similar directions.
- Vector database (Qdrant): stores those vectors and quickly finds the nearest ones to a query.
- Cosine similarity: measures the angle between two vectors. Near 1 = very similar meaning.
- Chunking: one vector per whole document blurs topics together, so split into passages and
  embed each one.
- Payload: metadata stored next to each vector (source document, type, chunk number). It lets
  you filter results.


3. PIPELINE, STEP BY STEP
-------------------------
data/raw (240 files) -> Clean -> Chunk -> Embed -> Qdrant -> Search

STEP 1 - DATA (scripts/generate_corpus.py)
- The corpus is SYNTHETIC, generated by a script with fixed seed 42. It is NOT official RBI or
  NPCI text, and the README says so. Say this out loud in the presentation.
- 4 document types, 240 raw files, 6 duplicates -> 234 unique documents:
    28 guidelines
    22 playbooks (one per fraud type)
    92 investigator notes
    92 chargeback narratives
- Files are deliberately NOISY (headers, "Page n of m" footers, smart quotes, double spaces,
  Windows line endings, duplicate files) so the cleaning step has real work.

STEP 2 - CLEANING (src/sentinel_rag/cleaning.py)
  1. Normalise unicode (NFKC), turn smart quotes into plain ASCII.
  2. Convert line endings and form feeds.
  3. Drop boilerplate lines (header, footer, disclaimer) with regexes.
  4. Collapse extra whitespace.
  5. Drop near-empty files; remove EXACT duplicates by SHA-256 of the cleaned text.
  6. Take the title from the first line. The FOLDER NAME becomes doc_type, so a different
     corpus can be dropped in with the same layout.

STEP 3 - CHUNKING (chunking.py)  <- most likely to be asked about
- Size 900 characters (about 200 tokens). Overlap 150 characters (about 17%).
- Sentence-aware: packs whole sentences until the 900 limit, never cuts mid-sentence.
  Headings stay attached to the sentence after them.
- Overlap carries the last sentences of one chunk into the next. Many rules read "X applies IF
  Y within Z days", and overlap keeps the condition with the rule.
- Why 900 (README says measured on this corpus):

    Size / overlap   Chunks   Problem
    500 / 80         472      Separates a case's observations from its outcome
    900 / 150        270      CHOSEN
    1500 / 250       238      Merges unrelated guideline sections, diluting the vector

- At 900, most chargebacks and case notes fit in ONE chunk. Guidelines and playbooks split into
  2-4 chunks along section boundaries. Median chunk = 661 characters.

STEP 4 - EMBEDDING (embeddings.py)  <- the non-obvious details
- Model: Gemini Embedding 2, 3072 dimensions. Your run used "gemini-embedding-2-preview"
  through the Euron EURI gateway (OpenAI-compatible endpoint, uses the openai SDK). A direct
  Google provider is also supported.
- TASK PREFIXES GO IN THE TEXT (this model has no task_type field):
    documents: "title: {title} | text: {chunk}"
    queries:   "task: search result | query: {question}"
  Prefixing the title also gives each chunk its document's context.
- ONE VECTOR PER CHUNK: passing the Google API a plain list of strings returns ONE combined
  vector for the whole list. The code sends one Content object per chunk and checks that the
  vector count equals the chunk count and each vector has 3072 dimensions.
- Reliability: retries with exponential backoff on 429/503. A local cache stores every vector,
  so re-runs are free and resume after interruption.
- A fake hashed bag-of-words embedder lets the tests run offline with no API key.

STEP 5 - QDRANT STORAGE (store.py)
- Collection: sentinel_corpus. Vector size 3072 (must match the model exactly). Distance Cosine.
- Point IDs: UUIDv5 of "source_document#chunk_number". The same chunk always gets the same ID,
  so re-running ingest OVERWRITES instead of duplicating (idempotent). Good point to mention.
- Payload: source_document, doc_type, chunk_number, total_chunks, title, text.
- Payload indexes on doc_type, source_document, chunk_number. Qdrant Cloud requires an index on
  any field you filter by.

STEP 6 - SEARCH (scripts/search.py)
- Embed the query with the query prefix, then query_points with limit=5.
- Filtered search adds a Filter: doc_type = investigator_note.
- Output is saved to results/search_results.md and .json.

5. WEAK SPOTS - BE READY FOR THESE
----------------------------------
Raising them yourself makes you look more credible than having someone else find them.

1. Q6 ranked a digital-arrest note above the SIM swap playbook. Scores around 0.70 are close
   together and short case notes are semantically generic. Fixes: hybrid keyword + vector
   search, a reranker, or boosting playbooks.
2. Q10 returned only chargebacks. The UPI chargeback guideline (which describes merchant
   evidence) did not appear. The 92 near-identical chargeback narratives crowd out the 28
   guidelines. The synthetic corpus is imbalanced.
3. The duplicate cleaner keeps the "-copy" file. Q8 returns pb-digital-arrest-copy.txt as the
   source. Files are sorted alphabetically and "-copy" sorts before ".txt", so the copy is read
   first and the original is dropped. Content is identical, but the source name looks odd.
   One-line fix: prefer the shortest filename.
4. Scores are fairly flat (0.68-0.82). Normal for Gemini embeddings. Compare scores relatively,
   not against an absolute threshold.
5. There is no LLM answer step yet. This is retrieval only. The "G" in RAG would be the next
   stage: pass the top 5 chunks to a model to write a grounded answer with citations.

7. LIKELY Q&A
-------------
- Why characters, not tokens?  No tokenizer download needed, easy to explain. 1 token is about
  4 characters in English.
- Why cosine?  Embeddings are compared by direction; Google recommends it for these vectors.
- Why overlap?  So a rule and its condition are not split across a boundary.
- Why a payload index?  Fast filtered search; Qdrant Cloud strict mode requires one.
- What if you re-run ingest?  Deterministic IDs overwrite existing points, and the cache avoids
  paying for the same embeddings again.
- How is it tested?  pytest runs offline with in-memory Qdrant and the fake embedder. It checks
  cleaning, 200+ docs, chunk size and overlap, idempotent upsert, top-5 search and the filter.
